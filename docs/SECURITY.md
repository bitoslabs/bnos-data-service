# Security

## 1. Assets

| Asset | Sensitivity | Where |
| --- | --- | --- |
| Access/refresh tokens | High | Client memory/session storage; server stores hashes |
| Invite/setup codes | High (one-time) | Server stores hashes; shown to admin once |
| Organization encryption keys | Critical | Never sent to this service in v1 |
| Raw private events | High (ciphertext) | PostgreSQL |
| Report aggregates | Medium | PostgreSQL |
| Membership and workspace metadata | Medium | PostgreSQL |
| Audit trail | High integrity | PostgreSQL |

## 2. Threat model

| Threat | Mitigation |
| --- | --- |
| Stolen access token | Short TTL, revocation, hashed storage, no logging |
| Refresh token replay | Rotation + reuse detection revokes the family |
| Invite brute force | 256-bit codes, hashed, single-use, TTL, rate limit |
| Challenge replay | Single-use nonce, TTL, audience and workspace binding |
| Cross-tenant access | Workspace from session, scoped queries, optional RLS |
| Forged events | Canonical id + Schnorr signature verification |
| Malicious payload | Envelope shape validation, size caps, kind allowlist |
| Server breach exposing data | Private content is ciphertext; keys never stored |
| Metadata leakage | Documented; minimize what is logged/returned |
| DoS via large batches | Body limits, batch cap, per-IP/per-key rate limits |
| SSRF via service URL | Server never fetches arbitrary URLs for clients |
| Dependency compromise | Lockfile, pinned versions, minimal dependency tree |
| Backup loss | Encrypted backups, restore drills, verified evidence only |

Explicit non-goal: protecting against a compromised client device. The client
holds the organization key and can decrypt its own data.

## 3. Authentication

### 3.1 Invites

- Generated by the admin CLI, shown once, never logged.
- 32 random bytes, base64url; stored as `sha256`.
- Bound to a workspace, optional pubkey, permissions, and a TTL.
- Single use: atomically mark `used_at` on successful verify.
- Compare hashes in constant time.

### 3.2 Challenge/response

- Challenge TTL <= 5 minutes.
- Nonce is single use and bound to audience, workspace, pubkey, and
  `challengeId`.
- Verify the full signed event: canonical id, Schnorr signature, tags, method,
  URL, audience, workspace, and timestamp skew.
- Mark the challenge used **before** issuing tokens, in the same transaction.
- On any failure return `401` without distinguishing which check failed.

### 3.3 Sessions

- Access token TTL: 15–60 minutes (default 15).
- Refresh TTL: 30 days, rotating on each use.
- Store only `sha256(token)` and `sha256(refreshToken)`.
- Re-check membership on refresh; revoked members cannot refresh.
- Logout revokes the access session and, if supplied, the refresh token.
- On identity/workspace switch the client drops tokens; the server must also
  reject tokens whose workspace no longer matches the membership.
- Never accept tokens from query strings or cookies.

### 3.4 CORS and CSRF

- Bearer tokens only, no cookies, so classic CSRF does not apply.
- Restrict `Access-Control-Allow-Origin` to configured app origins.
- Allow only `GET, POST, OPTIONS`, headers `authorization, content-type`.
- Never reflect arbitrary origins.

## 4. Authorization

- Derive `workspace_id` and `pubkey` from the validated session.
- Never trust workspace, organization, or branch values from the body or tags.
- Verify the event `organization` tag (when present) equals the session workspace.
- Enforce permissions per route (`backup.write`, `reports.read`, `status.read`).
- In cloud, enforce plan quotas without discarding accepted data.
- Optional Postgres RLS as defense in depth; application scoping is mandatory.

## 5. Event validation

For every event, before persistence:

1. Field types and hex lengths (`id`, `pubkey`, `sig`).
2. Canonical id matches the serialized event.
3. Schnorr signature verifies against `pubkey`.
4. Kind is in the deployment allowlist.
5. `created_at` is not far in the future; historical values allowed for backfill.
6. Event JSON size and batch size are within limits.
7. Private mode: `content` is a valid encryption envelope.
8. Reject unknown/extra envelope keys to prevent smuggling plaintext.

Never deserialize or trust `content` beyond shape validation; never execute or
render it server-side.

## 6. Encryption envelope validation

Accept only the organization-key AES-256-GCM envelope:

- `v === 1`, `encrypted === true`
- `scheme === "org.bitos.bnos.organization-key.v1"`
- `alg === "AES-256-GCM"`
- `kid` is a bounded string without control characters
- `nonce` is canonical base64url, exactly 12 bytes
- `ciphertext` is canonical base64url, bounded length
- optional `aad` contains only `recordId`, bounded and without control characters
- no other keys

Mirror the client guard in `src/lib/data-service/queue.ts` so a client bug cannot
cause accidental plaintext upload. If plaintext ingest is ever enabled for
public catalog events, gate it behind an explicit flag and kind allowlist.

## 7. Rate limiting and resource limits

- Global body limit and per-event size cap.
- Batch cap (100 events, matching the client).
- Per-IP and per-pubkey request limits; per-workspace ingest quotas.
- Challenge and invite endpoints rate limited aggressively.
- `@fastify/under-pressure` for load shedding with `503` (the client retries).
- Database statement timeout and pool bounds.
- Report query range and bucket caps.

## 8. Logging and observability

- Log request id, route, status, duration, workspace id (hashed or truncated as
  policy requires).
- Redact `authorization`, invite codes, tokens, and any decrypted content.
- Never log event `content` or raw signatures in normal operation.
- Audit security-relevant actions: invite creation, connect, disconnect,
  restore drill, membership change, server decryption opt-in.
- Keep audit entries append-only from the app's perspective.

## 9. Data protection

- TLS everywhere; HSTS at the proxy.
- Disk encryption for PostgreSQL and backups.
- Encrypted backups; keys managed outside the database.
- Retention policy explicit per deployment/plan.
- Secure deletion on workspace removal (rows, partitions, backups, derived
  projections) with an audit record.
- Report snapshots contain aggregates; treat them as confidential business data.

## 10. Metadata leakage

Even with encrypted content, the service sees and stores:

- pubkeys and workspace/location identifiers,
- event kinds and timestamps,
- record ids (`d` tags),
- ciphertext sizes and upload timing.

Document this in the client privacy notice. Do not add fields that expand
leakage without a review.

## 11. Backup and restore

- Back up PostgreSQL with WAL archiving or scheduled encrypted dumps.
- Test restores regularly; record `last_verified_restore_at` only then.
- A successful health check is not restore evidence.
- Backups must not contain plaintext organization keys (they never reach the
  server in v1).
- Verify backup integrity with checksums and periodic restore drills.

## 12. Deployment hardening

- Run as non-root, read-only root filesystem where possible.
- Distroless or slim runtime image; no build toolchain in production.
- Least-privilege database role (no superuser, no DDL at runtime).
- Secrets via environment/secret manager, never committed.
- Disable unused Fastify routes and verbose errors in production.
- Pin dependencies; enable automated vulnerability scanning.
- Keep Node.js and PostgreSQL patched.

## 13. Security checklist

- [ ] Invite codes hashed, single-use, expiring.
- [ ] Challenge nonce single-use, TTL, audience/workspace bound.
- [ ] Event id and signature verified for every event.
- [ ] Workspace from session on every query.
- [ ] Tokens hashed at rest; rotation and reuse detection.
- [ ] Envelope validation rejects plaintext and extra keys.
- [ ] Rate limits and body/batch caps enabled.
- [ ] CORS allowlist and security headers configured.
- [ ] Logs redact secrets and content.
- [ ] No decryption path in v1.
- [ ] Backups encrypted; restore drill verified before advertising it.
- [ ] Audit log covers connect, invite, disconnect, restore, membership.
